# Part A｜详情页叙事填写手册

## A1 五段骨架逐段指引

骨架固定五段（**背景与约束 → 我的角色 → 关键决策与取舍 → 结果 → 复盘**），由 MDX 模板固化（见 02 设计 §9 T06）。下面每段给：写什么 / **不要写什么** / 建议字数 / 合格与不合格对照。

### 段 1｜背景与约束（120–200 字）

**写什么**：系统原来什么样；在什么约束下工作（规模、预算、人力、deadline、不能动的遗留系统）；不解决会怎样。约束必须能落到数字或不可协商的条件上。

**不要写什么**：
- ❌ 公司/业务介绍——"某平台是国内领先的一站式购物平台"
- ❌ 没有边界的困难——"随着业务快速发展，系统面临巨大挑战"
- ❌ 解决方案——背景段出现"因此我们引入了 Kafka"就越界了

**合格**："日均订单 120 万，履约链路跨 4 个下游系统，其中库存与物流只提供 HTTP 轮询、没有回调。大促期 P95 延迟 40s，用户在下单页看到的『备货中』最长要等 1 分钟。团队 3 个后端，Q4 前不能停机迁移，两个下游当年内不会改造。"

**不合格**："随着业务高速发展，订单系统压力越来越大，亟需优化以支撑业务持续增长。"

> 判断标准：合格句里每个名词都能被追问（谁的 40s？哪 4 个系统？），不合格句一句都问不下去。

### 段 2｜我的角色（80–150 字）

**写什么**：你 own 什么、不 own 什么、和谁协作、决策权到哪。动词用"我决定 / 我否决 / 我推动 / 我评估后放弃"。

**不要写什么**：
- ❌ 职级与头衔——`role` 字段已经写了
- ❌ "参与"——读者无法判断你的贡献边界
- ❌ 把团队成果写成一己之力，别人做的部分要标明

**合格**："我负责履约状态机与端到端延迟预算（状态流转、重试与幂等、压测口径）。下游接口改造由我出方案并推动排期，有提议权、无决定权；容量评估与限流阈值由 SRE 定，我不做基础设施决策。团队 2 名后端由我分配任务与评审。"

**不合格**："参与了订单履约系统的架构设计与开发工作，负责后端相关模块。"

### 段 3｜关键决策与取舍（250–400 字，重点）

**写什么**：2–3 个真实决策，每个写成 **有哪些选项 → 为什么选这个 → 为此放弃了什么**。至少一个被否方案，否决理由要具体到代价，不能是"不合适"。

**不要写什么**：
- ❌ 技术栈罗列——"使用 Kafka 保证高可用，Redis 做缓存"
- ❌ 最佳实践式表述——"遵循领域驱动设计拆分服务"
- ❌ 没有代价的决策——选了 A 且毫无损失的多半不是决策，是默认路径

**合格**（完整版见 A3「关键决策与取舍」）："履约确认原本与下单在同一条同步链路上，下游抖动会让用户卡在支付页。两条路：推动下游加回调（对方排期满，否决）、网关侧变更探测（可行）。选后者，代价是自己维护探测频率与差量窗口，延迟 40s → 约 8s。"

**不合格**："技术选型上采用 Kafka 作为消息中间件、Redis 作为缓存层，并通过合理的服务拆分提升了系统的可扩展性和稳定性。"

> 段 3 是唯一"越长越好"的一段：读者就是来看取舍的，压到 200 字以下基本等于没写。

### 段 4｜结果（100–200 字）

**写什么**：把 `metrics[]` 逐条翻成句子，一条一句，**先指标、后方法**（句式见 A2）。没有数字的写可观察行为变化并明确标注。

**不要写什么**：
- ❌ 模糊副词——"显著提升/大幅优化"（schema 会直接报错）
- ❌ 无法归因的全局指标——"GMV 提升 30%"，读者会连带怀疑其他数字
- ❌ 把"上线了"当结果——"项目顺利上线并稳定运行"

**合格**（三条完整写法见 A3「结果」）："履约延迟 P95 从 40s 变为 3s（衡量方式：埋点 + BI 看板，2024-10~11 全量流量）；『状态不一致』工单从日均 220 张降到 12 张（客服工单系统按该标签统计）。"

**不合格**："重构后系统性能显著提升，用户体验大幅改善，获得了业务方的一致好评。"

### 段 5｜复盘（100–200 字）

**写什么**：哪条判断事后看是错的；重来会怎么改；留下什么债。一条错判 + 一条改法 + 一条债就够。

**不要写什么**：
- ❌ 正确的废话——"未来会继续关注性能优化，不断提升稳定性"
- ❌ 感谢团队
- ❌ 只写外部原因——"因为排期紧张所以没做灰度"，读者只会觉得你没判断

**合格**："最大的误判是把下游兼容窗口估短了：首次上线没做灰度，3% 的订单在『已支付未履约』停留超过 5 分钟，靠回滚 + 补单兜住。重来会先对 5% 流量开探测、观察 48 小时再全量，并把回滚演练写进上线清单——这次的清单是上线后才补的。技术债：差异比对逻辑散在 3 个 handler 未抽成模块，每加一个字段要改 3 处。"

**不合格**："项目整体达到了预期目标，过程中的一些挑战都通过团队努力克服了，未来会继续优化。"

## A2 `metrics` 的三种句式（补齐 02 设计 §2.3 未覆盖的情形）

02 设计 §2.3 已定字段与基础句式（`{label} 从 {baseline} 变为 {value}` + `衡量方式：{method}`），这里只补它没覆盖的两种降级情形，以及 `direction` 的判定规则。

**情形 1｜`baseline` 与 `value` 齐全（首选）**

> `{label} 从 {baseline} 变为 {value}（衡量方式：{method}）`
> 卡片摘要句用：`{value} 的 {label}`

例：履约延迟 P95 从 40s 变为 3s（衡量方式：埋点 + BI 看板，2024-10~11 全量流量）。

**情形 2｜只有 `value`，没有 `baseline`（历史数据拿不到）**

> `{label} 达到 {value}（口径：{method}）`

关键是**把口径写全**（数据源 + 分位 + 时间窗 + 样本），让读者能自己判断这个数的分量。
例：首屏 LCP 达到 1.8s（口径：CrUX 移动端 75 分位，2026-09 全量真实用户）。

❌ 错误降级：把"达到 1.8s"写成"LCP 大幅优化"——一旦丢了 `method`，数字就失去可信度；这也是 `method` 在 schema 层被设为必填的原因。

**情形 3｜连数字都拿不到（只能给可观察变化）**

此时 `value` 不写数字，写**"谁的行为发生了什么改变"**，并在正文里明确标注这是可观察变化、不是度量结果：

> `{label} 从 {baseline} 变为 {value}` → 写成「`{label}`：原先 {旧行为}，现在 {新行为}（可观察变化，非度量结果）」

例：
- `label`: 下游系统改造方式 / `baseline`: 4 个系统均为 HTTP 轮询 / `value`: 3 个改为回调，1 个保留探测 / `method`: 下游接口清单 + 上线后 30 天轮询告警为零
- 正文写法："4 个下游系统里有 3 个从轮询改为回调，第 4 个保留探测机制（可观察变化，非度量结果；口径：接口清单 + 上线后 30 天轮询告警为零）。"

⚠️ 情形 3 的条目**不要指望进首页 `ProofStrip`**：它只取 `featured` 项目里 `baseline` 齐全的条目，无 `baseline` 抽不到——这是设计取舍，不是缺陷。

**`direction` 怎么填**

| 指标语义 | 填 | 例 |
|---|---|---|
| 延迟、错误率、成本、体积、工单数、构建时长 | `down` | 履约延迟 P95（40s → 3s） |
| 吞吐、覆盖率、转化率、可用性、测试通过率 | `up` | 单机 QPS（800 → 2600） |
| 说不清方向（如"技术栈数量"、"系统个数"） | **不填** | 不填则不渲箭头；硬填会被 lint 判方向矛盾（`warn`） |

注意：`direction` 只描述"数值变大还是变小"，**不是"变好还是变坏"**。延迟下降是 `down`，不要因为"这是好事"就填 `up`。

## A3 完整示范项目：`order-pipeline`

> 说明：项目与数据均为虚构（脱敏表述），但结构与字段严格按 02 设计 §2.3 的 `ProjectFrontmatter` 写。正文约 1050 字，是 8–12 篇的目标尺度。下方五段标题在 MDX 里写作 `##`（索引按 `##` 切块，见 02 设计 §7.4），此处降为 H4 以便阅读。

**front matter（摘要部分）**

```yaml
title: 实时订单履约管道          # ≤16 字
slug: order-pipeline
summary: 把履约确认的 P95 延迟从 40s 压到 3s，支撑日均 120 万单的大促峰值。   # 40–120 字
ogTagline: P95 延迟 40s → 3s     # ≤24 字，仅 OG 图第 2 行
role: 后端负责人（带 2 人）
period: { start: 2024-03, end: 2024-11 }
team: 3 后端（含我）+ 1 SRE + 1 产品
company: 某电商平台
stack: [TypeScript, Postgres, Redis, Kafka]
status: shipped
featured: true
order: 10
tags: [性能, 稳定性]
confidentiality: 客户与订单数据已脱敏，指标为同量级近似
updatedAt: 2026-10-02
metrics:
  - label: 履约延迟 P95
    baseline: 40s
    value: 3s
    method: 埋点 + BI 看板，2024-10~11 全量流量，日均 120 万单
    direction: down
  - label: 「状态不一致」客服工单
    baseline: 日均 220 张
    value: 日均 12 张
    method: 客服工单系统按该标签统计，改造前 2024-08 全月对比上线后 2024-10~11
    direction: down
  - label: 单均履约调用次数
    baseline: 7 次
    value: 2 次
    method: 网关访问日志按订单号聚合，抽样 10 万单
    direction: down
```

**正文**

#### 背景与约束

2024 年初，某电商平台的订单履约链路要跨 4 个下游系统（库存、支付、物流、消息），其中库存与物流只提供 HTTP 轮询接口，没有回调。大促期间日均订单 120 万，履约确认的 P95 延迟 40s，用户在下单页看到的"备货中"最长要等 1 分钟。硬约束有三条：团队只有 3 个后端，Q4 前不能停机迁移；两个下游接口当年内不可能改造（对方排期已满）；客服侧"状态不一致"工单日均 220 张，是当时最大的投诉来源，必须在双十一前压下去。

> 用到字段：`period`（时间背景）· `company`（脱敏主体）· `stack`（未出现，属正常——背景段不必报技术栈）

#### 我的角色

我负责履约状态机与端到端延迟预算，包括状态流转规则、重试与幂等策略、以及压测口径的制定。两个下游接口的改造由我出方案、写清收益与风险并推动对方排期——这部分我有提议权、没有决定权。容量评估与限流阈值由 SRE 提供，我不做基础设施决策。团队里 2 名后端由我分配任务与评审。

> 用到字段：`role`（职责范围，正文展开为"own 什么 / 不 own 什么"）· `team`（协作规模）

#### 关键决策与取舍

**决策一：用探测模拟事件，而不是等下游改造。** 履约确认原本与下单在同一个同步链路里，任何下游抖动都会让用户卡在支付页。有两条路：推动下游加回调（对方排期已满，否决）；在网关侧做变更探测，用短轮询 + 差异比对模拟事件（可行）。我们选了后者，代价是自己维护探测频率与差量窗口，延迟从 40s 降到约 8s——**够不够用这件事，当时还没想清楚**。

**决策二：把履约确认摘出同步链路，走 Kafka。** 好处是下游抖动不再传导给用户；代价有三条：履约从"同事务内可见"变成最终一致（通常 3s 内），前端必须新增"处理中"状态，这直接改了产品交互；多了一套消息重放与死信处理，运维复杂度上升；状态机必须做成幂等（以 `orderId + 版本号` 做键），否则重放会重复扣减库存。

**被否的方案：编排引擎。** 我们评估过用 Temporal 这类编排引擎统一管理状态流转，模型更干净、可视化更好。否决理由是引入新组件 + 团队无人有生产经验，故障时排查成本不可控。最终用"状态机表 + 定时对账"替代，能力弱一档，但可解释、能在现有监控里看见。

> 用到字段：`stack`（Kafka 在此处出现才有意义——因为它是一个被权衡过的选项，不是装饰）

#### 结果

履约延迟 P95 从 40s 变为 3s（衡量方式：埋点 + BI 看板，2024-10~11 全量流量，日均 120 万单）。"状态不一致"工单从日均 220 张降到 12 张（客服工单系统按该标签统计，改造前 2024-08 全月对比上线后 2024-10~11）。单均履约调用次数从 7 次降到 2 次（网关访问日志按订单号聚合，抽样 10 万单）。另有一项无法量化的变化：产品侧不再需要为"支付成功但未履约"做专门的安抚文案（可观察变化，非度量结果）。

> 用到字段：`metrics[]` 三条逐条落地（label / baseline / value / method / direction 全部对应）；`confidentiality` 决定这段可以写多细

#### 复盘

最大的误判是把两个下游的兼容窗口估短了：第一次上线没做灰度，3% 的订单在"已支付未履约"状态停留超过 5 分钟，最后靠回滚 + 补单兜住。如果重来，我会先只对 5% 流量开探测，观察 48 小时再全量，并把回滚演练写进上线清单——这次的上线清单是上线后才补的。技术债：差异比对逻辑散在 3 个 handler 里没抽成模块，后来每加一个字段要改 3 处，这个债到现在还在还。

> 用到字段：`confidentiality`（3% 这类数字是否需要脱敏，取决于该字段怎么填）

## A4 三组「不合格 → 合格」改写对照

### 组 1｜只有职责没有决策

**原文**
> 负责订单履约系统的开发与维护，参与架构设计，保障系统稳定运行。

**诊断**：整句只说明"这个岗位存在过"，没有一个可以追问的判断。

**改写**
> 履约确认与下单绑在同一条同步链路上，任何下游抖动都会让用户卡在支付页。我做了两个判断：一是先用网关侧探测把延迟从 40s 压到 8s，不等下游改造（对方排期已满）；二是把履约确认摘出同步链路走 Kafka，接受"最终一致 + 前端新增处理中状态"的代价，换来下游抖动不再传导给用户。

**为什么能过 lint**：出现了两个可归属的决策点，各自带"放弃了什么"；对应 `metrics` 有 `value` 与 `method`，`check-content.mjs` 的模糊词正则（`显著|大幅|明显|很多|若干`）不会命中。

### 组 2｜只有"显著提升"没有方法

**原文**
> 重构后接口性能显著提升，大幅优化了用户体验，获得业务方认可。

**诊断**：三重不可核验——"显著提升"没有基线与结果、"用户体验"没有观测口径、"业务方认可"没有任何可查证的痕迹。

**改写**
> 履约延迟 P95 从 40s 变为 3s（衡量方式：埋点 + BI 看板，2024-10~11 全量流量，日均 120 万单）；"状态不一致"工单从日均 220 张降到 12 张（客服工单系统按该标签统计）。

**为什么能过 lint**：`value` 为具体数值且无模糊词；`method` 写全了数据源 + 时间窗 + 样本范围（三者缺一，人工复核即打回）；`direction: down` 与"40s → 3s"方向一致，不触发方向矛盾 `warn`。

### 组 3｜只有技术栈罗列没有取舍

**原文**
> 使用 Kafka、Redis、Postgres、TypeScript 构建高可用分布式系统，支持水平扩展。

**诊断**：技术名是"我用过什么"的证据，不是"我会判断"的证据；四个名词排在一起，等于没有一个被认真权衡过。

**改写**
> 选 Kafka 不是为了"高可用"，而是为了把履约确认从同步链路里摘出去：代价是履约变成最终一致（通常 3s 内），前端要新增一个"处理中"状态，状态机也必须做成幂等（`orderId + 版本号`），否则重放会重复扣减。Redis 只用来存探测窗口的差量指纹，不存业务状态——状态以 Postgres 的状态机表为准，避免两处真相。

**为什么能过 lint**：`stack` 里每个技术都在正文有对应的"为什么选它 / 为什么不用它做另一件事"，技术栈不再与正文脱节；同时写清"状态以 Postgres 为准"，避免 `summary` 与正文两处口径互相否定（人工 review 最常见的退回原因）。

## A5 提交前自查清单（10 条，逐条勾）

- [ ] 1. `summary` 是否同时包含"做了什么"和"带来什么"，且在 40–120 字之间？
- [ ] 2. 每条 `metrics.value` 是否是数字或**明确标注的可观察变化**，且不含"显著/大幅/明显/很多/若干"？

## B2 判定口径（怎样算一条通过）

**分阶段判定，不要混着算。**

| 阶段 | 判什么 | 不判什么 |
|---|---|---|
| Phase 1（检索直出，无 LLM） | 只判 `hit@3` 与 `unknown-accuracy` | 不判语气、不判可读性、不判"答得完整不完整" |
| Phase 2（检索 + 组答） | `hit@3` + `unknown-accuracy` + `citation-validity` | `P@1` 只作为趋势观察，不作为门槛 |

**`hit@3`（单条）**
- 判据：`expect_slugs` 中**任意一个**出现在返回的前 3 条里 → 该条 `hit = true`。
- 两个期望 slug 的题（对比型）额外记两列：`partial`（只中 1 个）与 `full`（2 个都中）。**门槛只看任意命中**，但 `full` 率必须单独报——Phase 1 是片段直出，两个都出现才真的回答得了"对比"。
- `expect_slugs: []` 的边界题**不参与 `hit@3` 分母**（否则会被算成永久失败）。

**`unknown-accuracy`（边界题）**
- 判据：返回 `no_match`（或 Phase 2 明确说明"站内没有相关信息"）→ 通过；返回了不相关片段却没有下结论 → **记 fail**（宁可严：对边界题"沉默地给一堆东西"和"编造"一样糟）。
- 分母 = 当前边界题总数（会随补题增长，不写死 5）；补题时**原有 5 条必须保留**，不允许"删掉答不好的边界题再补新题"——那是换题不是进步。
- 人工复核项：即使判 `no_match`，也要看有没有附带错误肯定（例如"站内没有 iOS 项目，但有移动端 Web 经验"——这是合格的澄清；"他有 iOS 开发经验"——这是幻觉，整题 fail）。

**`citation-validity`（Phase 2 才启用）**
- 判据：返回的每个出处链接必须（a）能打开，（b）被引用的片段确实出现在该页面（脚本抓取后做子串匹配）。任一条失效 → 整题 fail。
- 常见失效：引用了 `/projects/xxx` 但片段来自 `resume`，或角标指向了列表页而非详情页锚点。

**汇总与门槛**

```
hit@3            = 命中条数 / 15          # 20 条里 15 条有 expect_slugs
unknown-accuracy = 边界题通过数 / 5
citation-validity= 有效出处条数 / 全部出处条数   # Phase 2
```

Phase 2 上线门槛（与 02 设计 §7.7 一致）：`hit@3 ≥ 0.8`（即 ≥12/15）且 `unknown-accuracy = 1.0`（全对）。不达标就留在 Phase 1；**唯一不被允许的动作是调低门槛**。

## B3 使用方式

1. **落地**：复制 B1 的 YAML 到 `docs/ai-eval/questions.yaml`，把 `expect_slugs` 换成实际 slug（题面不要改）。
2. **跑分**：`pnpm eval:ask`（`scripts/eval-ask.mjs`），CI 里作为**非阻塞**日报，不阻断合并——正文内容改动会自然影响命中，阻断式门禁会让人不敢改内容。
3. **节奏**：Phase 1 上线后**每周跑一次**；每次新增/大改项目详情后立刻补跑一次（BM25 索引变了，历史分数不可比）。
4. **补题**：每周从日志里取 `hit=false` 的真实问题，人工标注期望 slug 后追加 1–3 条，目标是 **30 条**；补到 30 条后冻结为 `v1` 并把分数作为基线，此后只允许在"新增项目"时同步加题。
5. **归档**：每次跑分把 `{日期, 题数, hit@3, partial/full, unknown-accuracy, 版本}` 记一行到 `docs/ai-eval/history.md`，用于回答"这次内容改动有没有把检索弄坏"。
